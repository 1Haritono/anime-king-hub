# Workspace Rules

## Git Workflow Rules

Каждый раз при внесении изменений в код (правки, фичи, фиксы, рефакторинг) необходимо строго следовать следующим правилам Git:

### 1. ПЕРЕД ИЗМЕНЕНИЯМИ
- Проверить, является ли директория git-репозиторием (наличие `.git`).
- Если нет git — спросить пользователя, инициализировать ли (`git init`), не делать молча.
- Выполнить `git status` / `git diff` для понимания уже внесенных правок.

### 2. ПОСЛЕ ЛОГИЧЕСКОГО БЛОКА РАБОТЫ — КОММИТ
- Не копить несколько независимых задач в один коммит.
- Одно логическое изменение = один коммит (например, сначала `fix`, затем `feat`).
- **Не коммитить секреты** (`.env` с токенами, ключи, пароли). Проверять `.gitignore`.
- Перед коммитом проверять `git status` и `git diff`.

### 3. ФОРМАТ СООБЩЕНИЙ КОММИТОВ (Conventional Commits)
- Сообщения на английском/русском языке в соответствии с репозиторием (по умолчанию краткий английский).
- Типы:
  - `feat:` новая возможность
  - `fix:` исправление бага
  - `refactor:` рефакторинг без смены поведения
  - `style:` форматирование
  - `docs:` документация
  - `chore:` конфигурация / зависимости / инфраструктура
  - `perf:` оптимизация производительности
  - `build:` сборка / electron-builder / CI
- Тема: до ~72 символов, без точки на конце.

### 4. КОГДА НЕ КОММИТИТЬ САМОМУ
- Пользователь явно указал «не коммитить».
- Репозиторий в неясном состоянии с неотносящимися чужими правками.

### 5. ТЕГИ И РЕЛИЗЫ
- Теги и GitHub Releases создаются ТОЛЬКО при явном запросе пользователя на выпуск релиза.
- Соблюдать semver в `package.json`.

### 6. PUSH
- `git push` выполнять ТОЛЬКО по прямому запросу пользователя или если задача явно требует публикации.
